## Exploration: deletion-and-trash (soft delete, trash/restore, purge, book-history trace)

### Current State

Node deletion does not exist today (`docs/TODO.md` Finding 2026-09-09, answered 2026-09-17). The schema cascades **by accident**, not by choice:

- `nodes_parent_fk` (`packages/db/drizzle/0001_tenancy.sql:68`) is `ON DELETE CASCADE` on `parent_id` — deleting a node recursively deletes its whole subtree.
- `page_content` cascades from `nodes` via a 3-col FK `(node_id, workspace_id, node_type)` (`0008_page_content.sql`). `page_blocks`, `page_revision`, `comments`, `page_locks` all cascade from `page_content`. `links.sourcePageId`, `page_tags.pageId`, `chunks.pageId` cascade from `page_content`/`nodes`; `links.targetPageId` is `ON DELETE SET NULL`; `permissions.resource_id` cascades from `nodes`. `changeset.book_id` cascades from `nodes` too, so a purged book takes its whole changeset/revision history with it — consistent with the owner's decision (a book's history has no purpose without the book).
- `nodes_parent_slug_unique (parent_id, slug)` is an **unconditional** unique constraint (`0001_tenancy.sql:72`) — this is the exact collision point for "restore when the name was reused."
- `path` is a trigger-maintained (`nodes_set_path`), CHECK-constrained materialised ancestry string used **only** for subtree navigation (`packages/db/src/nodes/subtree.ts`, the one module allowed to write a `path LIKE` predicate — `scripts/checks/query-boundaries.ts` rule 2). Authorization never reads it (design decision D5, `docs/SPECS.md` §14) — it walks `parent_id` via a recursive CTE instead (`packages/db/src/permissions/resolver.ts`). This matters: a trash flag on `nodes` does not have to touch the authorization path at all.
- Every tree/backlink/mention/activity surface already follows one absence-vs-denial precedent: a single `notFound()` helper returning the same 404 body regardless of "doesn't exist" vs "exists, can't read" (`apps/api/src/routes/tree.ts`, `comments.ts`'s "Listing without disclosure"). A trash filter has to be added at every one of these read sites without missing one, or a trashed node leaks through a surface nobody remembered.
- Comments already have a first-class terminal-but-visible state, `orphaned` (comment-threads spec, `packages/db/src/comments/reconcile-comments.ts`) — a close in-house precedent for "gone but auditable, one-way transition, never revived automatically." `page_blocks` has an actual DB-trigger-enforced one-way transition (`0016_page_blocks_no_resurrection.sql`, `page_blocks_forbid_resurrection`) — good precedent for making trash/purge terminal at the storage layer, not just in application code.
- `packages/db/src/ai/reindex.ts` is the existing "explicit tracked job" idiom (`queued|running|completed|failed`, idempotent completion under a `WHERE state IN (...)` guard) — the direct template for a purge job, though purge is simpler (no generation bookkeeping needed, just a periodic sweep that is naturally idempotent: deleting an already-gone row is a no-op).
- `apps/web/app/composables/useTreeRowActions.ts` explicitly has **no delete action today**, with a header comment pointing at the (now-closed) three open questions — this is the file to extend.
- `useConfirm`/`ConfirmDialog` (`apps/web/app/composables/useConfirm.ts`, `apps/web/app/components/ConfirmDialog.vue`) is the product's one confirm dialog, promise-based, with a `tone: 'destructive'` already supported — but `ConfirmOptions` has **no typed-text-match field**, so "type the container's name to force-delete" needs either extending this one dialog's contract with an optional confirm-text-match, or a second purpose-built destructive dialog (tension with the "one confirm dialog" philosophy stated in its own header comment).
- `apps/web/app/components/ManagementSidebar.vue` is the existing pattern for a Trash screen's home.
- `packages/db/src/nodes/create.ts`/`rename.ts` share `resolveSiblingSlug()` — the one place slug-collision is decided; restore must reuse or mirror this, not reinvent it.

### Affected Areas

- `packages/db/src/schema.ts`, `packages/db/drizzle/00NN_*.sql` — new column(s)/table(s), the partial-unique-index change on `nodes_parent_slug_unique`, and (optionally) a small append-only deletion-trace table.
- `packages/db/src/nodes/subtree.ts` — descendant counting for "N pages will be deleted" must go through here (query-boundaries.ts rule 2 forbids a second `path LIKE` writer).
- `packages/db/src/nodes/create.ts`, `rename.ts`, `move.ts` — slug-uniqueness and legality checks need trash-awareness.
- `packages/db/src/permissions/resolver.ts` — likely untouched (walks `parent_id`, not affected by a trash flag), but must be re-verified once a container-delete/force-delete/restore action needs a `manage`-gated check.
- `apps/api/src/routes/tree.ts`, `comments.ts`, `links.ts` (backlinks), `mentions.ts`, `activity.ts`, `revisions.ts`, `diff.ts` — every read surface must exclude trashed nodes/pages; a new trash-listing/restore route needs the opposite filter, gated by `manage`.
- `packages/ai-tools` / MCP surface (`list_tree`, `get_page`, `get_backlinks`) — same non-disclosure obligation extends here; not yet inspected file-by-file, flagged as a follow-up read before `sdd-design`.
- `apps/web/app/composables/useTreeRowActions.ts` — add the Delete action (disabled+reason when non-empty, for a non-owner).
- `apps/web/app/composables/useConfirm.ts`, `apps/web/app/components/ConfirmDialog.vue` — force-delete's typed-name step.
- `apps/web/app/components/ManagementSidebar.vue` and a new Trash page — restore surface.
- `packages/db/src/comments/reconcile-comments.ts`, `revisions/queries.ts` — no anchor logic changes expected (anchors stay valid while a page sits in trash, since `page_content`/`page_blocks` remain live rows); purge simply cascades them away with the node, per the owner's decision.
- `scripts/checks/query-boundaries.ts`, `single-source.ts`, `diff-input-purity.ts` — guardrails a new trash module must not trip (see Risks).

### Approaches

1. **`trashed_at` timestamp on `nodes`, propagated to the whole subtree at trash time** — cascade-based hard purge after 30 days reuses the existing (already-flagged-as-accidental) `ON DELETE CASCADE` chain, now exercised deliberately.
   - Pros: `nodes` stays the single structural source of truth (matches the project's own stated allergy to duplicated facts — `LEGAL_PARENT_TYPES`, `NodeType`, enforced by `single-source.ts`); restore is a one-column flip, no re-insertion or id churn; permission resolver untouched (walks `parent_id` regardless); comments/revisions need zero schema change — they simply cascade away at purge time exactly as decided; purge job is a trivial, naturally-idempotent periodic sweep (`DELETE FROM nodes WHERE trashed_at < now() - interval '30 days'`).
   - Cons: `nodes_parent_slug_unique` must become a partial index (`WHERE trashed_at IS NULL`) or trash-time slugs must be rewritten — real migration surface, and every consumer of `resolveSiblingSlug` needs review; every existing read site touching `nodes`/`page_content`/`comments`/`links`/mentions must add a trash filter and it is easy to miss one (this is the main risk); "empty to delete" and "N pages will be deleted" must treat already-trashed descendants as absent, so `subtree.ts` needs a trash-aware descendant query; the permanent book-history trace ("page X deleted by Y") needs its own append-only record independent of the node, because the node itself is gone after purge while the book's history must still say the deletion happened — this needs a small new table/record type in either approach.
   - Effort: Medium — mostly mechanical filter additions plus one focused migration, but wide surface area (many call sites) raises the "did we get all of them" review cost.

2. **Separate `trashed_nodes` (or `trash`) table — physically move the row(s) out of `nodes` at delete time, restore re-inserts**
   - Pros: `nodes` keeps a live-only invariant — zero risk of a forgotten `trashed_at IS NULL` filter anywhere, since every existing reader of `nodes` needs no change at all; slug collision during the trash window disappears by construction (the row simply is not in `nodes`), matching "restore must handle slug uniqueness among siblings when the name was reused" cleanly at restore time instead of via a partial index.
   - Cons: every composite FK anchored to `nodes(id, workspace_id[, type])` — `page_content`, `permissions`, `chunks`, `changeset` — is `ON DELETE CASCADE` from `nodes`; physically removing the row cascades comments/revisions/permissions away **immediately**, at trash time, not at the 30-day purge — directly contradicting the owner's "comments and revisions go with it" (implying they survive the trash window) and "a hard delete never runs against an audit trail on demand" for 30 days, unless every one of those FKs is restructured (a much bigger schema change than a partial index); restoring a multi-node subtree means re-inserting N rows with exact ids/positions/parents atomically, re-validating that the parent still exists (it may have been moved, renamed, or itself purged in the 30-day window) — materially harder than a timestamp flip; creates a second `NodeType`-shaped table, which is exactly the duplicated-fact pattern this codebase has repeatedly burned itself on (`LEGAL_PARENT_TYPES` written twice, closed by `single-source.ts`) — the Trash screen's own hierarchy display would need a `nodes UNION trashed_nodes` reconstruction that only gets more awkward the longer something sits in trash.
   - Effort: High — schema surgery on nearly every FK anchored to `nodes`, plus a materially harder restore path, for a benefit (no missed-filter risk) achievable more cheaply with a partial unique index in Approach 1.

### Recommendation

**Approach 1** (`trashed_at` on `nodes`, propagated to the trashed subtree, `nodes_parent_slug_unique` made partial, a small append-only deletion-trace record independent of the node for the permanent book-history line). It keeps the single-source-of-truth discipline this codebase already enforces structurally (`single-source.ts`), reuses rather than fights the existing cascade chain (turning "cascades by accident" into "cascades on purge, by choice" — exactly what the 2026-09-17 decision asks for), and is a mechanical (if wide) extension of read sites that already share one absence/denial helper pattern per route file. Approach 2's isolation benefit is real but is bought at the cost of breaking the very cascade the owner's decision relies on to make comments/revisions disappear together with the page at purge time, not before.

Two points need explicit resolution in `sdd-design` before `sdd-tasks`, because they are not fully determined by the two node-storage options above:
- **The book-history trace record.** It must outlive the purge (survive after the deleted page's row, and its `page_content`/`comments`/`page_revision` rows, are gone), so it cannot be a plain FK-cascaded child of the deleted node. A small, append-only table keyed to the **book** (not the deleted page) holding `{ bookId, deletedNodeId (no cascading FK, or ON DELETE SET NULL), deletedTitle snapshot, deletedByUserId, deletedAt }` is the natural fit — following the same "terminal, one-way, storage-layer enforced" idiom as `page_blocks_forbid_resurrection`.
- **The `manage`-gated visibility of a trashed node.** Decision 5 states the permission is `manage` on the node (or the owner force-delete rule), which is a *stronger* gate than the `read` used everywhere else in the tree; the Trash screen's own listing endpoint is therefore a genuinely new access pattern (list what a subject can `manage`, not what they can `read`) worth designing deliberately rather than reusing `readableResourceIds` as-is.

### Risks

- **Missed trash filter.** The single biggest risk of Approach 1: every one of tree, backlinks, mentions, activity, revisions, comments, diff, and the MCP surface (`list_tree`, `get_page`, `get_backlinks`, `search_workspace`) must independently add a `trashed_at IS NULL` (or ancestor-trashed) condition; forgetting one leaks a "deleted" page. This needs either a single shared helper (mirroring `readableResourceIds`) or an explicit checklist gated by a structural-check equivalent to `query-boundaries.ts`.
- **Slug-uniqueness migration.** Converting `nodes_parent_slug_unique` to a partial index is a real migration on a live constraint with existing rows and existing tests (`nodes/create.test.ts`, `rename.test.ts`) asserting the current unconditional behaviour.
- **Force-delete count correctness.** `subtree.ts`'s descendant query must be made trash-aware so "N pages will be deleted" both (a) does not count already-trashed descendants and (b) is computed through the one sargable path module, not a second ad hoc query.
- **MCP/agent surface not yet read file-by-file** — `packages/ai-tools` was not inspected in this pass; its tool implementations must be confirmed to route through the same trashed-filter helper before `sdd-design` closes this out.
- **`query-boundaries.ts` / `single-source.ts` / `diff-input-purity.ts` compliance** — a trash-aware subtree count must not become a second `path LIKE` writer (rule 2); a trash-listing/restore route must still resolve through `packages/db/src/permissions/` (rule 1), never a parallel permission check; no new `NodeType`-shaped table should appear (weighs directly against Approach 2); nothing in this feature should touch `block_index`/`blockIndex` outside the existing diff modules (rule 8 territory).
- **`ConfirmDialog` scope creep.** The typed-name force-delete step does not fit the current `ConfirmOptions` contract; deciding whether to extend the one shared dialog or add a second destructive-only component is a real product/UI decision, not purely mechanical (`docs/UI-CHECKLIST.md`/`DESIGN-SYSTEM.md` review required before shipping either).

### Ready for Proposal

Yes. The three product decisions the 2026-09-09 finding was blocked on are closed (2026-09-17), the schema/cascade mechanics are fully mapped, and both viable storage approaches are compared with a clear recommendation. The two open design points above (the trace record's shape, and the `manage`-gated trash listing) are appropriately sized for `sdd-design`, not blockers to `sdd-propose`.

**Is `sdd-research` (external evidence) worth it?** Low value, optional. This is an internal architecture decision fully determined by this codebase's own schema, FK graph, and existing precedents (the `orphaned` comment state, the `page_blocks` one-way trigger, the `reindex` job idiom) — no external library or protocol choice is in question. The one place a fast external check could de-risk something is BookStack's own "Recycle Bin" restore behavior when a parent was deleted or renamed in the interim (deep-wiki explicitly draws its hierarchy lineage from BookStack, `docs/SPECS.md` §1) — a single, short lookup rather than a full `sdd-research` pass would suffice if the owner wants that precedent before `sdd-design` decides the restore-onto-a-changed-parent behavior.
